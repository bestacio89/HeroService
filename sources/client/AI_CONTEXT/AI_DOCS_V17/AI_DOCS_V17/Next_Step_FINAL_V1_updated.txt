V18 — état complet, historique consolidé et prochain contexte de reprise

Résumé exécutif
Le prototype Unity MOBA 5v5 dispose désormais d'un socle runtime stabilisé, d'une minimap V1.1 validée, d'un flux pré-match MVP relié au runtime, d'une transition UX propre vers le gameplay, d'un vrai start flow runtime avec countdown UI et d'un HUD gameplay complet pour le héros local.

Depuis V17, les validations suivantes ont été ajoutées sans casser le socle existant :
- `CountdownUIPresenter` affiche le countdown `3, 2, 1, GO` centré à l'écran dans le HUD runtime
- `CountdownUIPresenter` se masque automatiquement après le GO (HideAfterDelay)
- `MatchStartFlowController` orchestre le presenter : Show() avant le countdown, Hide() en sécurité à l'entrée InGame
- `LocalHeroHUDPresenter` résout les composants du héros local via GameManager.OnMatchStarted
- barres HP et mana affichées avec valeurs numériques exactes et fill horizontal
- niveau du héros local affiché
- overlays de cooldown radiaux sur SkillOneButton, SkillTwoButton, UltimateButton
- timers numériques de cooldown sur les boutons skills (entiers, style Mobile Legends)
- AttackButton sans overlay/timer — décision de design validée (CD trop court, non pertinent)
- `HeroWorldUI` (world space) coexiste avec le HUD screen space — les deux sont actifs

Ce document doit être considéré comme la vérité opérationnelle pour reprendre le projet dans une nouvelle conversation IA.

H. Décisions d'architecture critiques
- `GameManager` = source de vérité match-level
- `HeroSpawner` = orchestrateur runtime
- `HeroSelectionSessionService` = source de vérité pré-match
- `MatchBootstrapper` = passerelle pré-match → runtime
- `PreMatchRuntimeTransitionController` = transition UX/runtime uniquement
- `MatchFlowSystem` = propriétaire du start flow runtime
- `CountdownController` = exécution technique du countdown
- `CountdownUIPresenter` = affichage passif du countdown, piloté par MatchStartFlowController
- `LocalHeroHUDPresenter` = affichage passif du HUD héros local, résolution via GameManager
- `PlayerInputGate` = autorisation d'input gameplay locale
- UI = lecture / orchestration passive
- pas de logique gameplay métier dans les vues UI
- slots résolus par nom (transform.Find) — jamais par GetComponents sans ordre garanti
